# Right Place, Wrong Time: Temporal-Support Error Is the Unmeasured Half of Event–RGB Benchmarks

*Team 08 — attack angle: the evaluation. CVPR 2027 (deadline ~Nov 2026).*

---

## One-sentence thesis

Every event / event–RGB benchmark scores a prediction against a ground truth that lives on a *different clock with a different temporal support*, and every metric in use (mAP, EPE, PSNR, 3D AP) is a scalar over a single nominal instant, so the dominant error mode under fast motion — being at the right place along the object's path but at the wrong time — is silently accounted as spatial error; we give an identifiable decomposition of published error into a spatial part (pixels ⟂ to the motion) and a temporal-support part (milliseconds ∥ to the motion), re-score released checkpoints with it, and show the ranking is not the ranking mAP reports.

---

## The assumption we kill

**Named assumption — the *Instantaneous-State Assumption* (ISA):**

> A benchmark tuple `(prediction ŝ, ground truth s*, query time t)` is evaluated as `ρ(ŝ, s*)` under the assumption that both `ŝ` and `s*` are the state of the world *at the single instant t*.

Formally, let a predictor `P` emit a state from a data window with a normalized temporal support kernel `k_P` (how much of the emitted state's information comes from each past instant), with centroid `c_P = ∫u·k_P(u)du` and width `w_P = 2√(∫(u−c_P)²k_P)`. Let the ground-truth process `G` have its own kernel `k_G`. ISA is the claim `c_P = c_G = 0` and `w_P = w_G = 0`. **No published event benchmark states, enforces, or checks this. It is false in every case we examined, and the violation is on the order of 25–50 ms — one to three object diameters at automotive speeds.**

### Why it is universal (verified, with sources)

| Benchmark | What the GT clock actually is | `k_G` |
|---|---|---|
| **Prophesee 1 Mpx** (Perot et al., NeurIPS 2020) | Boxes come from a **commercial automotive detector run on a side-mounted GoPro Hero6 at 60 fps**, then warped to event pixels by a homography. Paper: *"Labels are first extracted from the RGB camera and then transferred to the event camera pixel coordinates by using a geometric transformation… we observed time synchronization errors smaller than the discretization step Δt."* | GoPro exposure ⊛ RGB-detector response ⊛ an unquantified sync offset ⊛ parallax |
| **Prophesee GEN1** | Boxes drawn by humans on **ATIS grey-level images built by aggregating asynchronous per-pixel intensity measurements**; labels at 1/2/4 Hz. Each pixel's grey value is integrated over an intensity-dependent interval, so the "image" the annotator saw has no single timestamp. | per-pixel, intensity-dependent integration window |
| **DSEC-Detection** (Gehrig & Scaramuzza, *Nature* 2024) | *"labels are generated by running a state-of-the-art object tracking algorithm on the rectified image frames"* (QDTrack on 20 fps RGB), warped into the event view, then manually cleaned. Inter-frame labels: *"We generate inter-frame labels by **linearly interpolating** the position … and size … of each object."* | 20 Hz RGB exposure ⊛ tracker ⊛ **triangular interpolation kernel of half-width 50 ms** |
| **DSEC-3DOD / Ev-Waymo** (Cho et al., CVPR 2025 **Highlight**) | 10 FPS LiDAR-clock 3D boxes; the advertised **100 FPS** GT is: *"We **linearly interpolated** the original 10 FPS annotations, dividing blind times into 10 evenly spaced intervals… we employed **event-based video frame interpolation** and point cloud interpolation methods to generate sensor data for blind time. Data annotation experts refined interpolated bounding boxes."* | LiDAR sweep ⊛ linear motion prior ⊛ **a VFI network's own temporal prior** |
| **DSEC-Flow / MVSEC** | GT flow defined *between two frame timestamps* (10 Hz / dt=1,4), i.e. GT is a displacement over a 100 ms **interval**, not a state at an instant. MVSEC is documented in the flow literature as *lacking temporal synchronization with the ground truth*. | 100 ms interval + sensor-pose interpolation |
| **BS-ERGB / HS-ERGB (event VFI)** | PSNR against a real skipped frame **with a finite exposure**. A prediction that is correctly sharp at the exposure centre is *penalised* relative to one blurred over the exposure. The metric rewards agreement with the GT's support, not with the world. | camera exposure |

Two corollaries the field has not stated:

1. **The high-rate ground truth of the two flagship "low-latency" event benchmarks is a linear motion model.** DSEC-Det inter-frame labels are pure linear interpolation; DSEC-3DOD 100 FPS labels are linear interpolation seeded and then refined against VFI-synthesised sensor data. Inter-frame mAP therefore partly measures *agreement with a constant-velocity prior*, and a method whose motion model is genuinely nonlinear is penalised for being right.
2. **Representations with a constant *event count* have a temporal support whose width is a function of scene activity.** Faster motion → more events → shorter window → different support centroid. So `c_P` is itself a function of speed, i.e. the timing bias is confounded with the exact variable that makes it matter. No metric in the field can see this.

We verified from source that the standard event detector protocol places the event window's **end** exactly at the label time. In `uzh-rpg/RVT`, both `config/dataset/gen1.yaml` and `gen4.yaml` set `ev_repr_name: 'stacked_histogram_dt=50_nbins=10'`, and `scripts/genx/preprocess_dataset.py` asserts `frame_ts_us == ev_repr_timestamps_us_end[repr_idx]`. So the network sees events over `[t−50 ms, t]` and is scored on the state at `t`: **for a uniform event rate the information centroid of the input is `t − 25 ms`.** That is a *prediction*, not a hypothesis — see §4 (C3).

## The failure phenomenon

### The one plot

**Measurement.** For every matched (prediction, GT) pair produced by a *published* checkpoint, take the box-centre error `e = ĉ − c*(t)` and project it onto the GT track's unit tangent `û(t)`:
`e_∥ = ⟨e, û⟩`, `e_⟂ = e − e_∥û`.

**Independent variable.** The object's ground-truth image speed `‖v*(t)‖` (px/ms), binned; and the dimensionless **support-mismatch number** `M = ‖v*‖·(w_G+w_P)/2 / d`, `d = √(wh)` (how many object diameters the object moves during the benchmark's own admitted timing ambiguity).

**Axes.** Panel A: x = `‖v*‖`, y = **signed mean** `e_∥` (px). Panel B: same x, y = mean `‖e_⟂‖` (px). Panel C: histogram of `M` over each test set.

**Expected curve.** Panel A is, for each method, a **straight line through the origin whose slope is that method's latency in milliseconds**. Panel B is roughly flat. Panel C is a mass concentrated at `M < 0.1` with a thin tail.

That is the whole indictment in three panels: the error that grows with speed is *entirely* in one direction, that direction is the motion direction, the growth rate is a time, and the test set is built so that this time is invisible.

## The reformulation

### 1. The unit of error changes

Current unit: **pixels** (or dB, or IoU). Proposed unit: an ordered pair **(pixels ⟂ to motion, milliseconds ∥ to motion)**. A pixel is not a time; a benchmark whose only unit is the pixel cannot report a time, which is why the field has no number for its own dominant failure.

### 2. The geometric identifiability argument

A *timing* error is a **one-parameter** perturbation: a single scalar `δ` must simultaneously explain the box translation (`δ·v*`), the box scale change (`δ·ṡ*`), the aspect change, and — in 3D — the yaw change. A *spatial* error is unconstrained (2 or 7 DoF). Therefore the temporal hypothesis is **testable, not assumed**: we fit one `δ` per object and check whether it explains all channels. This is the property that separates our decomposition from an arbitrary re-parameterisation.

### 3. The decomposition

For a matched pair on a GT track with velocity `v*(t) ≠ 0`, `û = v*/‖v*‖`, `s = √(wh)`:

```
e      = ĉ − c*(t)                                  ∈ ℝ²
e_∥    = ⟨e, û⟩                                     (px, signed)
e_⟂    = e − e_∥ û                                  (px, vector)
δ̂      = e_∥ / ‖v*(t)‖                              (ms)          [translation channel]
ε_s    = log( ŝ / s*(t) )
δ̂_s    = ε_s / ( d log s*/dt )                      (ms)          [scale channel]
κ      = |δ̂ − δ̂_s| / (σ_δ̂ + σ_δ̂_s)                  (consistency, O(1) under H_temporal)
```

Per-method latency, weighted least squares through the origin over all matched pairs in a slice (weights `w_i` = inverse GT-velocity variance):

```
τ̂_P = Σ_i w_i e_∥,i ‖v*_i‖ / Σ_i w_i ‖v*_i‖²
```

Also fit with a free intercept `b`; `b` is genuine, speed-independent spatial bias (calibration, parallax, event–RGB extrinsics). Reporting `(τ̂, b)` separates "your model is late" from "your warp is wrong" — currently both land in `loc` error.

### 4. The metric family, and why the relaxation budget is not a knob

```
τ_max := (w_G + w_P) / 2          # HALF THE UNION OF THE TWO DECLARED SUPPORTS
```

**The relaxation budget is derived from the benchmark's own specification and the method's own declared aggregation window — not tuned.** For RVT on Gen1, `w_P = 50 ms` and `w_G` is the ATIS integration width; for DSEC-Det inter-frame, `w_G = 50 ms` (the interpolation half-width, stated by the authors). This removes the single largest degree of freedom a hostile reviewer would attack.

```
AP        : standard.
AP^sync   : re-anchor every prediction by ĉ ← ĉ − τ̂_P · v̂_pred, where v̂_pred is estimated
            from the METHOD'S OWN consecutive outputs (never from GT), then score normally.
            Δ_clock = AP^sync − AP        # error from a CONSTANT clock offset
AP^⟂      : before IoU matching, translate each prediction along the GT tangent by the amount
            minimising the distance, clipped to |δ| ≤ τ_max.
            Δ_TS = AP^⟂ − AP^sync         # error from PER-OBJECT, time-varying support error
AP^iso    : identical, but the translation direction is free (disc of radius ‖v*‖τ_max).  CONTROL.
R         : (AP^⟂ − AP) / (AP^iso − AP)   ∈ [0,1]      ANISOTROPY
```

By construction `AP ≤ AP^sync ≤ AP^⟂ ≤ AP^iso`. **We never claim `AP^⟂` is "the true score".** The contributions are (i) the *triple* `(AP, τ̂, AP^⟂)` replacing the scalar, (ii) the *gaps* `Δ_clock, Δ_TS`, (iii) the anisotropy `R` which is the falsifiable statement that the gap is temporal rather than slack, and (iv) the **change of ranking** between `AP` and `AP^⟂`.

Flow version (identical algebra, `Δt` = the GT interval):
```
û = f*/‖f*‖ ;  δ̂ = ⟨f̂ − f*, û⟩ · Δt / ‖f*‖ ;  EPE_⟂ = ‖(f̂ − f*) − ⟨f̂−f*,û⟩û‖
```
An event flow method that systematically under-scales its flow — the single most common flow failure — is then reported as *estimating displacement over an effective interval shorter than `Δt`*, which is a physically meaningful and actionable statement that "EPE 0.79" is not.

### 5. The protocol: **TS-Split** and the three GT variants

**TS-Split.** Report every metric stratified by deciles of `M = ‖v*‖·τ_max/d`, and report the top-`M` decile as a headline slice (`AP@HiM`). This is the "benchmark slice where the temporal component is identifiable" — it requires no new data, only a re-partition of existing test sets, and it is computable from GT alone.

**Three-GT release (TSB-Sim).** For the controlled half we render a small simulated set (ESIM/v2e on a Blender scene with analytic object trajectories, 1000 fps base rate, exposure formed by explicit integration) and release **three ground truths for the same sequences**:
- `GT_inst(t)` — the true state at the instant `t` (only obtainable in simulation);
- `GT_exp(t)` — the state as an exposure-integrated frame-clock annotator would record it;
- `GT_lin(t)` — the linear interpolation of `GT_exp` at anchor times, i.e. the benchmark-style GT.

Scoring the same predictions against all three, and reporting the spread, tells any future author **how much of their score is agreement with the annotation prior**. That is the constructive deliverable that outlives the paper.

**Reporting requirement we propose for the community.** A submission must declare `(c_P, w_P)` — the centroid and width of its temporal support — the way it currently declares FLOPs and latency. Two methods with different `w_P` are not comparable under a single mAP number, and today nothing forces anyone to say what `w_P` is.

### 6. The one "method" we allow ourselves — as a falsification test, not a contribution

**Temporal re-anchoring (≈ 5 lines, training-free, no GT at inference):** estimate each track's velocity from the method's *own* consecutive outputs, shift every box by `−τ̂_P·v̂_pred`. If the decomposition measures something real, this must recover most of `Δ_clock` **on the unmodified standard metric**. If it does not, our metric is measuring an artifact and we say so. We propose no architecture, no loss, no training. This is deliberately the weakest possible "method" — its only job is to be falsifiable.

## What existing methods cannot express

1. **A scalar over one nominal instant has no coordinate for "when".** mAP, EPE, PSNR and 3D AP are functions `ρ(ŝ, s*)`. There is no argument slot in which a timing offset could appear, so it is projected onto the only slot available — position — and reported as localisation error. TIDE's taxonomy (cls/loc/both/dup/bg/miss) is entirely *atemporal*: our whole phenomenon lives inside `loc`.
2. **No label format can state its own support.** `(x, y, w, h, t, class)` asserts a point in time. Nothing in DSEC-Det, GEN1, 1 Mpx, EventVOT or DSEC-3DOD records the exposure, the interpolation kernel, or the detector latency that produced `t`. A benchmark cannot report an uncertainty it has no field for.
3. **"Spatially the best, temporally the worst" is not expressible on any current event leaderboard.** Nor is its converse, which is the more dangerous case: a method that is spatially mediocre but happens to have a support centroid matching the annotator's wins.
4. **Constant-count representations have a speed-dependent support width.** Their `w_P` is a random variable driven by scene activity. There is no field, plot or metric anywhere in event vision that reports it, and mAP averages over it.
5. **The event-VFI case is the cleanest impossibility:** against a GT frame with finite exposure, PSNR *strictly prefers* a prediction blurred over the exposure to a prediction that is correctly sharp at the exposure centre. The metric cannot express "correct at an instant" because its reference is not an instant. Event cameras exist precisely to produce instantaneous states, and the metric structurally penalises that.
6. **Where the seed's phenomenon becomes visible:** "frames and events do not share the same temporal support" is currently expressible only as a *modelling* remark. In our units it becomes a *measurement*: `τ̂_event` vs `τ̂_frame` vs `τ̂_fused`, in milliseconds, from released checkpoints.

## Experimental plan

Everything is **inference-only on released checkpoints**. We train nothing. Every number derives from a dumped prediction file re-scored on CPU, exactly as TIDE does.

### E0 — Label forensics (zero GPU, days-1-to-2, highest indictment per unit cost)

Inputs: DSEC-Detection **Object Detection Labels (4.7 MB)** and DSEC-3DOD labels (from the 40.2 GB HF zip, labels only). Compute, per object:
- the deviation of the released high-rate GT from pure linear interpolation of its anchors;
- the IoU between released GT and the linear oracle (P7);
- the score of a **causal** constant-velocity extrapolator with no sensor data, evaluated under each benchmark's own published protocol.

Deliverable: the statement *"the inter-frame ground truth of the two flagship low-latency event benchmarks is, to within X% IoU, its own interpolation prior"* with X measured. No GPU, no download of event data.

### E1 — Detection: re-score released checkpoints on Gen1 and 1 Mpx

**Checkpoints (all links verified live, sizes measured by HTTP HEAD on 2026-09-01):**

| Method | Checkpoints | Host | Size |
|---|---|---|---|
| RVT-B / S / T (CVPR 2023) | `gen1/rvt-{b,s,t}.ckpt`, `1mpx/rvt-{b,s,t}.ckpt` | `download.ifi.uzh.ch/rpg/RVT/checkpoints/` | 223 MB (gen1-B), 297 MB (1mpx-B) |
| S5-ViT-B / S (Zubic et al., *CVPR 2024*, "State Space Models for Event Cameras") | `gen1_{base,small}.ckpt`, `gen4_{base,small}.ckpt` | `download.ifi.uzh.ch/rpg/CVPR24_Zubic/` | 219 MB each |

**Why this pairing is the fair-comparison guarantee:** `uzh-rpg/ssms_event_cameras` **consumes the identical preprocessed tarballs as RVT** (it links to the very same `gen1.tar` / `gen4.tar` URLs) and is built on the RVT codebase. Five model configurations, two datasets, **one data pipeline, zero re-implementation**. There is no preprocessing degree of freedom for a reviewer to attack.

**Data (sizes measured):** `gen1.tar` **98.63 GB**, `gen4.tar` **190.35 GB**, both live at `download.ifi.uzh.ch/rpg/RVT/datasets/preprocessed/`. No Prophesee registration needed for the preprocessed form. Total 289 GB of 990 GB free.

**Procedure.**
1. Reproduce each checkpoint's published headline mAP to within ±0.3 using the authors' own `validation.py`. **Publish the reproduction table.** Any checkpoint that fails reproduction is dropped, not fixed.
2. Dump per-detection predictions (score, box, query timestamp) to file. One inference pass per checkpoint — **no τ-sweep re-inference is needed**, because `δ̂ = e_∥/‖v*‖` estimates the offset at continuous resolution from a single pass.
3. Build GT tracks by Hungarian IoU association across consecutive label frames (1 Mpx labels come from a tracker, so association is near-exact); finite-difference for `v*` and `d log s*/dt`; discard pairs with unreliable velocity (`‖v*‖·τ_max < 2 px`).
4. Compute `(τ̂, b, AP, AP^sync, AP^⟂, AP^iso, R, Δ_clock, Δ_TS)` overall and per `M`-decile.

**GPU budget.** Gen1 (240×304): ≈ 1.5–2 h per model × 5 = **~9 GPU-h**. 1 Mpx (720×1280, downsampled ×2 by the released config): ≈ 4–5 h per model × 3 = **~14 GPU-h**. `batch_size.eval` reduced to 2–4 to stay under 9 GB; RVT-B at 240×304 batch 8 is well under 4 GB, 1 Mpx at batch 2 is ≈ 6 GB. All re-scoring is CPU.

### E2 — The headline controlled pair: BFlow `E` vs `E+I` on DSEC-Flow

**This is the experiment that speaks directly to the seed.** `uzh-rpg/bflow` releases, for the *same* architecture and training recipe, an **event-only** checkpoint `E_LU4_BD2.ckpt` (156 MB) and an **event+image** checkpoint `E_I_LU4_BD2.ckpt` (156 MB). The image branch's temporal support (frame exposure inside a 100 ms frame interval) is ~100× wider than the event branch's. Data: `bflow/DSEC/train.tar` **149.6 GB** (public GT; test GT is withheld by the benchmark server, so we use the authors' own train/val split and state the contamination caveat — contamination would *reduce* systematic timing bias, so our estimates are conservative). Also `E-RAFT` (`dsec.tar`, 64 MB; plus MVSEC 20 Hz and 45 Hz checkpoints — the same architecture at two different GT rates, a second controlled support manipulation, on MVSEC whose GT is fully public).

**Prediction:** `E+I` wins on EPE and **loses on `EPE_⟂`**, with `|τ̂_{E+I}| > |τ̂_E|`. If that holds, we have a published, author-released, single-variable demonstration that adding frames buys spatial accuracy by paying temporal-support error, and that the field's metric records only the credit. ≈ **2 GPU-h**.

### E3 — Event + RGB detection: DAGr on DSEC-Detection

`uzh-rpg/dagr` ships `dagr_s_50.pth` and, critically, **`run_test_interframe.py`, which already writes inter-frame detections to disk** — precisely the artefact our re-scorer consumes. Data: DSEC-Detection New Sequences **81.9 GB** + Remapped Images **34.1 GB** + Labels 4.7 MB (60 sequences, 70 379 frames, 390 118 boxes, with **track IDs**, which gives the cleanest velocity estimates of any dataset here). Report `τ̂` as a function of the offset within the 50 ms inter-frame interval — the prediction is a **sawtooth**: the effective latency grows across the interval and resets at each RGB frame. A sawtooth in `τ̂(t)` synchronised to the frame clock is a signature no spatial explanation can produce. ≈ **5 GPU-h**.

### E4 — Controlled half: TSB-Sim (ESIM/v2e, Docker)

~20 short Blender sequences with analytic object trajectories, base render 1000 fps, events via ESIM or v2e, RGB frames formed by explicit integration over a chosen exposure. Release `GT_inst`, `GT_exp`, `GT_lin` (§5). Uses: (i) **estimator calibration** — inject a known `τ` and verify `δ̂` recovers it with slope 1 (control C4); (ii) sweep `M` from 0.01 to 3, which no real dataset covers; (iii) demonstrate the event-VFI PSNR-prefers-blur impossibility with a concrete number. Fallback if ESIM is painful in Docker: `bflow`'s **MultiFlow** already has continuous-time trajectory GT (`val.tar` 325 GB — large but downloadable within the disk budget, and partial download suffices). ≈ **2 GPU-h** render + event generation.

**Total: ≈ 32–40 GPU-hours, every job under 9 GB VRAM, ~290–440 GB of disk, all inside Docker.** No training. The critical path is download bandwidth, not compute.

### Defence against "you just invented a metric your own method wins"

The strongest form of this defence is: **we do not propose a method.** Beyond that, five explicit controls:

- **C1 — Isotropic null (`AP^iso`, `R`).** An equal-budget *free-direction* relaxation upper-bounds ours. If `R ≈ 0.5`, our relaxation is just loosened IoU and we report the metric as vacuous. Per-pair version: `E[cos²θ]` between `e` and `û` is 0.5 under isotropic error; we report the full distribution and its bootstrap CI.
- **C2 — Coherence.** A timing error is coherent across objects; spatial noise is not. We test (i) that the per-frame mean of `δ̂` has variance far below the independent-noise prediction, and (ii) that the regression `e_∥ ~ τ·‖v*‖` has near-zero intercept. **A straight line through the origin whose slope is a time is not something a mis-specified metric produces.**
- **C3 — Pre-registered architecture prediction.** We predict `τ̂` from each method's *declared* temporal support **before measuring it** (RVT/S5-ViT: 50 ms window ending at `t` ⇒ centroid `t−25 ms` ⇒ `τ̂ ∈ [−35,−10] ms`), register the predictions in the supplement, and report hits and misses. Confirming a number predicted from architecture is the strongest available evidence that the metric measures a physical quantity.
- **C4 — Injection–recovery.** Inject a known offset (re-score against GT at `t+τ_inject`) and verify unit-slope recovery; report bias and variance of the estimator.
- **C5 — The falsification method.** Training-free temporal re-anchoring (§6) must recover most of `Δ_clock` **on the unmodified standard metric**. If it does not, we report that our metric failed its own test.

And one structural safeguard: **`τ_max` is not a free parameter** — it is `(w_G+w_P)/2`, read off the benchmark's and the method's own published specifications (§4).

## Risks

### Death 1 — The rankings do not flip

*Why it could happen:* published mAP gaps between the strongest pairs may exceed the temporal component; or all methods on a given dataset share the same 50 ms window and therefore the same `τ̂`, making the correction a uniform shift that preserves order.

*Mitigations, built in from the start:* (a) maximise the pool — 15+ checkpoints across 4 datasets gives ~100 orderable pairs; (b) target **deliberately controlled pairs** where a flip is mechanistically expected (BFlow `E` vs `E+I`; E-RAFT MVSEC 20 Hz vs 45 Hz; constant-count vs constant-duration representations), rather than hoping a flip appears among arbitrary methods; (c) report flips **on the `AP@HiM` slice**, where the temporal component is by construction largest and gaps are narrowest.

*Fallback if no flip survives:* the paper becomes *"the temporal component is large, systematic, predictable from architecture, and invisible to the metric — and here is the number for every published method"*. Paired with E0's result (the inter-frame GT is its own prior) and C3 (predicted `τ̂` confirmed), that is still a benchmark-integrity paper. It is weaker, and we say so. **A pure "no flip" outcome without E0 would not be publishable, which is why E0 runs first and independently.**

### Death 2 — The decomposition is not identifiable on real data

*Why:* velocities finite-differenced from 4 Hz (Gen1) or 10 Hz (1 Mpx preprocessed) labels are noisy; at low speeds `e_∥/‖v*‖` explodes; GT association fails on crowded scenes; the tangent direction is ill-defined for objects that are nearly stationary or that rotate.

*Mitigations:* restrict to pairs with `‖v*‖·τ_max > 2 px` and report the retained fraction; use the **scale channel** as an independent estimator (P4) — approaching objects give a scale rate even when lateral velocity is ~0; prefer DSEC-Detection (20 Hz labels **with track IDs**) as the primary velocity-rich testbed; and calibrate the estimator on TSB-Sim where velocity is exact (C4).

*Fallback:* if identifiability fails on real data, the paper narrows to **simulation + the DSEC-Det/DSEC-3DOD label forensics**, and the contribution becomes the protocol and the three-GT release rather than the re-scored leaderboard. Weaker, still constructive.

### Death 3 — "You are measuring the labels, not the models"

*Why it is the sharpest attack:* if `τ̂` is dominated by the annotation pipeline's own offset (GoPro sync error, QDTrack latency, ATIS integration), then every method on a dataset gets the same `τ̂` and we have measured the dataset, not the methods.

*Why that is survivable — and partly the point:* a *shared* `τ̂` is itself a publishable finding ("every 1 Mpx result in the literature is scored against labels offset by X ms"), and it is separable: the **dataset-level offset is the common component of `τ̂` across methods; the method-level offset is the residual.** We report both, with a variance decomposition across (dataset, method). The architecture prediction C3 discriminates: if `τ̂` tracks each method's declared window width, it is the method; if it is constant across methods with different windows, it is the dataset.

*Fallback:* run the whole analysis on TSB-Sim, where the label offset is zero by construction, to establish the method-level component cleanly, then transfer the estimator to real data.

### Death 4 (procedural) — Prior art we have not found

Our external verification was cut short by an exhausted search budget. The along-track/cross-track→latency conversion is standard in air-traffic surveillance and in trajectory prediction, and we already concede that. If someone has applied it as an *evaluation* metric in event vision, our contribution collapses to the protocol and the ranking evidence. **Mitigation: a full re-survey of 2025–2026 proceedings is the first task before any experiment, and E0 (which is independent of the decomposition's novelty) runs in parallel.**

*Next idea if the decomposition is taken:* pivot to **"the ground truth is a model"** — a paper that measures, for every major event benchmark, how much of a published score is explained by agreement with the label-generating process (linear interpolation, the RGB detector, the VFI network) rather than with the world, and releases a per-dataset "prior-agreement ceiling". E0 is already that paper's core experiment.
